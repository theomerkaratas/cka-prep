# Kubernetes Gateway API: Architecture, Personas, and Mechanics

The **Kubernetes Gateway API** is the next-generation standard for service networking, traffic routing, and ingress in Kubernetes. Maintained by the Kubernetes Network Special Interest Group (SIG-Network), it is designed as the official, modern successor to the traditional **Ingress** API (`networking.k8s.io/v1`).

While traditional Ingress successfully provided basic HTTP routing, large-scale enterprise adoption exposed deep architectural flaws. The Gateway API was engineered from scratch to resolve these limitations by introducing **role-oriented design**, **multi-protocol support**, and **declarative, portable advanced routing**.

---

## 1. Why Gateway API? Limitations of Traditional Ingress

To understand the Gateway API, you must understand why standard Ingress fell short:

1. **Monolithic Responsibility (Lack of Role Separation):**
   * In traditional Ingress, a single YAML object (`kind: Ingress`) defines infrastructure entry points (TLS certificates, public ports) AND developer routing rules (paths, backend services).
   * In real companies, cluster infrastructure (DNS, VIPs, firewall, TLS certificates) is managed by **Platform / DevOps Engineers**, while path routing (`/login`, `/api`) is managed by **Application Developers**. A developer editing a path could accidentally break cluster-wide TLS.
2. **Annotation Hell (Vendor Lock-in & Portability Issues):**
   * The core Ingress specification only supported basic host and path matching.
   * Any advanced feature—such as HTTP header rewrites, weighted traffic splitting (canary releases), rate limiting, or cross-namespace routing—required proprietary **Annotations** (e.g., `nginx.ingress.kubernetes.io/canary-weight: "20"` or `traefik.ingress.kubernetes.io/rate-limit`).
   * Because annotations are non-standard text strings, moving from an NGINX Ingress Controller to Envoy or Traefik required rewriting every Ingress manifest in the cluster.
3. **Protocol Limitations (HTTP/HTTPS Only):**
   * Traditional Ingress was strictly tied to Layer 7 HTTP and HTTPS. Exposing raw TCP (databases), UDP (DNS, game servers), or modern gRPC required custom, unstandardized workarounds.

## 2. The Core Architecture: Role-Oriented Design (Three Personas)

The Gateway API splits service networking across three distinct API resources, mapping cleanly to three organizational organizational roles (personas):

```text
┌────────────────────────────────────────────────────────────────────────┐
│ 1. GatewayClass (Infrastructure Provider: Cloud / Platform Admin)      │
│    - Defines the controller implementation (Envoy, Istio, Cilium)      │
│    - Cluster-scoped resource                                           │
└───────────────────────────────────┬────────────────────────────────────┘
                                    │ Created from
                                    ▼
┌────────────────────────────────────────────────────────────────────────┐
│ 2. Gateway (Cluster Operator / DevOps Engineer)                        │
│    - Defines entry points (VIP, Public IP, Ports 80/443, TLS Secret)   │
│    - Namespace-scoped (usually infra/gateway namespace)                │
└───────────────────────────────────▲────────────────────────────────────┘
                                    │ Attached via AllowedListeners
                                    ▼
┌────────────────────────────────────────────────────────────────────────┐
│ 3. HTTPRoute / GRPCRoute / TCPRoute (Application Developers)           │
│    - Defines routing rules (hosts, paths, headers, weighted splits)    │
│    - Lives in the application's private namespace (e.g., "team-a")     │
│    - Forwards traffic to backend Services                              │
└────────────────────────────────────────────────────────────────────────┘
```

### The Three Core Resources Explained:

| Resource | Scope | Managed By | Responsibility |
| :--- | :--- | :--- | :--- |
| **`GatewayClass`** | **Cluster** | Cloud Provider / Platform Architect | Defines the controller template (e.g., `example.com/gateway-controller`). Similar to `StorageClass` or `IngressClass`. |
| **`Gateway`** | **Namespace** | Cluster Operator / Network Admin | Defines actual listening interfaces: Ports, Protocol (`HTTP`, `HTTPS`, `TLS`, `TCP`, `UDP`), and TLS Secrets. Instantiates the load balancer. |
| **`HTTPRoute`** | **Namespace** | Application Developers | Defines request matching rules (`path`, `headers`, `method`), traffic transformations (filters, rewrites), and backend Services. |

---

## 3. Supported Protocols: Beyond HTTP

While traditional Ingress only knows HTTP/S, Gateway API introduces modular Route objects for multiple networking layers:

* **`HTTPRoute`:** Layer 7 HTTP/HTTPS routing (path, headers, query params, cookies, redirects, URL rewrites).
* **`GRPCRoute`:** Layer 7 native gRPC routing by service and RPC method.
* **`TLSRoute`:** Layer 4/7 SNI-based TLS passthrough (routing encrypted TLS traffic without decrypting it).
* **`TCPRoute`:** Layer 4 raw TCP forwarding (e.g., exposing MySQL, PostgreSQL, Redis).
* **`UDPRoute`:** Layer 4 raw UDP forwarding (e.g., DNS servers, Syslog, VoIP).

## 4. Gateway API Declarative Manifests & Mechanics

### Step 1: The `GatewayClass`
Usually pre-installed by the cluster networking provider (e.g., Cilium, Envoy Gateway, Google Cloud GKE Gateway Controller):

```yaml
apiVersion: gateway.networking.k8s.io/v1
kind: GatewayClass
metadata:
  name: eg-gateway-class
spec:
  controllerName: gateway.envoyproxy.io/gatewayclass-controller
```

---

### Step 2: The `Gateway` (Operator Defines Listeners)
The DevOps team creates a Gateway listening on port 80 and port 443:

```yaml
apiVersion: gateway.networking.k8s.io/v1
kind: Gateway
metadata:
  name: prod-gateway
  namespace: gateway-infra
spec:
  gatewayClassName: eg-gateway-class
  listeners:
    - name: http
      protocol: HTTP
      port: 80
      allowedRoutes:
        namespaces:
          from: All          # Allows developers in ANY namespace to attach routes
    - name: https
      protocol: HTTPS
      port: 443
      tls:
        mode: Terminate
        certificateRefs:
          - name: prod-wildcard-tls
      allowedRoutes:
        namespaces:
          from: Same         # Restricts HTTPS attachment to the same namespace
```

> [!IMPORTANT]
> **Cross-Namespace Route Attachment (`allowedRoutes`):**  
> Notice `allowedRoutes.namespaces.from`. This provides strict security boundaries. A Cluster Admin can configure a central Gateway in `gateway-infra` and grant permissions for application teams in `frontend` or `backend` namespaces to attach their routes without giving them admin access to the Gateway!

---

### Step 3: The `HTTPRoute` (Developer Defines Routing)
An application developer deploys an `HTTPRoute` inside their application namespace (`apps`):

```yaml
apiVersion: gateway.networking.k8s.io/v1
kind: HTTPRoute
metadata:
  name: store-route
  namespace: apps
spec:
  parentRefs:
    - name: prod-gateway
      namespace: gateway-infra
      sectionName: http
  hostnames:
    - store.example.com
  rules:
    - matches:
        - path:
            type: PathPrefix
            value: /products
      backendRefs:
        - name: product-service
          port: 8080
```

* **`parentRefs`:** Explicitly binds this route to the `prod-gateway` living in `gateway-infra`.
* **`rules.matches`:** Evaluates incoming requests for `store.example.com/products`.
* **`backendRefs`:** Forwards matching traffic to `product-service` on port 8080.

## 5. Built-in Advanced Routing: No More Annotations

Features that previously required messy vendor annotations are now **first-class declarative citizens** in Gateway API.

### Feature 1: Native Traffic Splitting (Canary / Blue-Green Deployments)
Splits traffic between v1 and v2 based on percentage weights without needing third-party tools like Flagger:

```yaml
rules:
  - backendRefs:
      - name: payment-svc-v1
        port: 8080
        weight: 90           # 90% of traffic to stable
      - name: payment-svc-v2
        port: 8080
        weight: 10           # 10% canary traffic
```

### Feature 2: HTTP Header & Method Matching
Routes requests to different backends based on headers (e.g., routing internal beta testers):

```yaml
rules:
  - matches:
      - headers:
          - name: X-Environment
            value: staging
      - method: POST
    backendRefs:
      - name: staging-service
        port: 8080
```

### Feature 3: Native URL Redirects & Rewrites (Filters)
No need for `nginx.ingress.kubernetes.io/rewrite-target`:

```yaml
rules:
  - matches:
      - path:
          type: PathPrefix
          value: /old-api
    filters:
      - type: URLRewrite
        urlRewrite:
          path:
            type: ReplacePrefixMatch
            replacePrefixMatch: /api/v2
    backendRefs:
      - name: modern-api-service
        port: 80
```

## 6. Architectural Comparison: Ingress vs. Gateway API

| Capability | Ingress (`networking.k8s.io/v1`) | Gateway API (`gateway.networking.k8s.io/v1`) |
| :--- | :--- | :--- |
| **API Architecture** | Monolithic (1 single object) | Decoupled & Role-Oriented (GatewayClass, Gateway, Route) |
| **Organizational Personas** | None (Devs and Ops share 1 file) | Distinct personas (Infrastructure Admin, Cluster Operator, App Developer) |
| **Supported Protocols** | HTTP / HTTPS only | HTTP, HTTPS, gRPC, TLS Passthrough, raw TCP, raw UDP |
| **Advanced Features (Weights, Headers)** | Vendor-specific non-portable annotations | First-class, standard YAML fields (`weight`, `filters`, `matches`) |
| **Cross-Namespace Routing** | Awkward / Vendor-specific hacks | Native, cryptographically validated via `ReferenceGrant` |
| **Conformance Validation** | Loose; behavior differs between controllers | Strict test suite enforced across all implementations |

---

## 7. Summary Reference

* **`GatewayClass`**: "Which controller engine runs the gateway?" (Cluster-wide)
* **`Gateway`**: "Where does external traffic enter? Ports, IPs, TLS certs." (Infra namespace)
* **`HTTPRoute`**: "How do URLs, headers, and paths route to Services?" (App namespace)
* **`ReferenceGrant`**: Security handshake permitting cross-namespace Secret or Service sharing.
