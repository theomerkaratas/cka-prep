# Kubernetes Gateway API: Architecture, Personas, and Mechanics

The **Kubernetes Gateway API** is the next generation of how traffic gets into a cluster and gets routed to your applications. It is maintained by the Kubernetes Network Special Interest Group (SIG-Network). You can think of it as the official, modern successor to the older **Ingress** API (`networking.k8s.io/v1`).

Ingress did a good job for simple HTTP routing. But when many companies and teams started using it at scale, its design showed serious problems. Gateway API was built from scratch to fix them. It does this with three ideas:

- **Role-oriented design:** different people own different parts of the setup.
- **Multi-protocol support:** not only HTTP, but also TCP, UDP, gRPC, and more.
- **Declarative, portable advanced routing:** features are written as normal Kubernetes fields, not as vendor-specific hacks.

> **Terms used in this document**
> - **Cluster:** a set of machines running Kubernetes.
> - **Namespace:** a logical group inside a cluster, used to separate teams or apps.
> - **Service:** a stable name and address that points to a group of Pods (the running containers of your app).
> - **Controller:** a program that watches Kubernetes objects and makes the real world match them. For example, a controller reads a Gateway object and actually starts a load balancer.
> - **Manifest:** a YAML file that describes Kubernetes objects.
> - **Layer 4 / Layer 7:** network layers. Layer 4 works with raw connections (IP addresses and ports, like TCP and UDP). Layer 7 understands application data, such as HTTP paths and headers.

---

## 1. Why Gateway API? Limitations of Traditional Ingress

To understand why Gateway API exists, it helps to see what was wrong with Ingress:

1. **One object, many owners (no separation of roles):**
   - In traditional Ingress, a single YAML object (`kind: Ingress`) defines both the entry point of the cluster (TLS certificates, public ports) and the developer's routing rules (paths, backend services).
   - In real companies, the platform or DevOps team manages the cluster entry point (DNS, public IPs, firewall, TLS certificates). Application developers manage path routing (`/login`, `/api`). If a developer edits a path in the same Ingress, they could accidentally break TLS for the whole cluster.

2. **Annotation hell (vendor lock-in and portability problems):**
   - The core Ingress specification only supports basic host and path matching.
   - Any advanced feature, such as rewriting HTTP headers, splitting traffic by weight (canary releases), rate limiting, or routing across namespaces, needed a vendor-specific **annotation**. Examples: `nginx.ingress.kubernetes.io/canary-weight: "20"` or `traefik.ingress.kubernetes.io/rate-limit`.
   - Annotations are plain text key-value pairs. Kubernetes does not check whether they are valid, and each controller understands its own set. So moving from the NGINX Ingress Controller to Envoy or Traefik meant rewriting every Ingress manifest in the cluster.

3. **Protocol limitations (only HTTP and HTTPS):**
   - Traditional Ingress was built only for Layer 7 HTTP and HTTPS. To expose raw TCP (for example a database), UDP (for example DNS or game servers), or gRPC, people had to use custom workarounds that were not standard.

## 2. The Core Architecture: Role-Oriented Design (Three Personas)

Gateway API splits the networking setup into three separate resources. Each resource is owned by a different role. A **persona** here just means "a type of person with a specific job."

```text
┌────────────────────────────────────────────────────────────────────────┐
│ 1. GatewayClass (Infrastructure Provider: Cloud / Platform Admin)      │
│    - Defines the controller implementation (Envoy, Istio, Cilium)      │
│    - Cluster-scoped resource                                           │
└───────────────────────────────────┬────────────────────────────────────┘
                                    │ Created from
                                    ▼
┌────────────────────────────────────────────────────────────────────────┐
│ 2. Gateway (Cluster Operator / DevOps Engineer)                        │
│    - Defines entry points (VIP, Public IP, Ports 80/443, TLS Secret)   │
│    - Namespace-scoped (usually infra/gateway namespace)                │
└───────────────────────────────────▲────────────────────────────────────┘
                                    │ Attached via parentRefs and allowedRoutes
                                    ▼
┌────────────────────────────────────────────────────────────────────────┐
│ 3. HTTPRoute / GRPCRoute / TCPRoute (Application Developers)           │
│    - Defines routing rules (hosts, paths, headers, weighted splits)    │
│    - Lives in the application's private namespace (e.g., "team-a")     │
│    - Forwards traffic to backend Services                              │
└────────────────────────────────────────────────────────────────────────┘
```

**How to read this diagram:** The arrows show how the objects depend on each other. The infrastructure provider sets up a `GatewayClass`. The operator creates a `Gateway` based on that class. The developer then creates routes that attach to that `Gateway`. Each person only works on their own layer, and the layers connect through references (names that point to other objects).

### The Three Core Resources Explained

| Resource | Scope | Managed By | Responsibility |
| :--- | :--- | :--- | :--- |
| **`GatewayClass`** | **Cluster** | Cloud Provider / Platform Architect | Defines the controller template (e.g., `example.com/gateway-controller`). Similar to `StorageClass` or `IngressClass`. |
| **`Gateway`** | **Namespace** | Cluster Operator / Network Admin | Defines the actual listening points: ports, protocol (`HTTP`, `HTTPS`, `TLS`, `TCP`, `UDP`), and TLS Secrets. Creating it makes the controller set up a real load balancer. |
| **`HTTPRoute`** | **Namespace** | Application Developers | Defines request matching rules (`path`, `headers`, `method`), traffic changes (filters, rewrites), and the backend Services that receive the traffic. |

**Scope** tells you where the object lives:
- **Cluster-scoped** objects exist once for the whole cluster, with no namespace.
- **Namespace-scoped** objects live inside one namespace.

## 3. Supported Protocols: Beyond HTTP

Traditional Ingress only understands HTTP and HTTPS. Gateway API adds separate Route objects for different protocols. Each Route type is for one kind of traffic:

* **`HTTPRoute`:** Layer 7 HTTP and HTTPS routing. It can match on path, headers, query parameters, and cookies, and it can do redirects and URL rewrites.
* **`GRPCRoute`:** Layer 7 routing for gRPC, a protocol used by many microservices. It matches on the gRPC service name and method name.
* **`TLSRoute`:** Layer 4 and 7 routing based on the SNI name (the server name sent at the start of a TLS connection). It forwards encrypted traffic **without decrypting it**. The backend handles the TLS itself. This is called **TLS passthrough**.
* **`TCPRoute`:** Layer 4 raw TCP forwarding. It does not look at the content. Useful for databases such as MySQL, PostgreSQL, or Redis.
* **`UDPRoute`:** Layer 4 raw UDP forwarding. Useful for DNS servers, Syslog, or VoIP.

## 4. Gateway API Declarative Manifests & Mechanics

**Declarative** means you describe the result you want in a YAML file, and Kubernetes and the controllers work out how to get there. You do not write step-by-step commands.

Every manifest in this section has the same top-level fields:

- **`apiVersion`:** the version of the Kubernetes API the object belongs to. For Gateway API it is `gateway.networking.k8s.io/v1`.
- **`kind`:** the type of object, such as `GatewayClass`, `Gateway`, or `HTTPRoute`.
- **`metadata`:** information about the object itself.
  - **`name`:** the unique name of the object in its namespace.
  - **`namespace`:** the namespace the object lives in. If it is missing, the object goes into the `default` namespace. `GatewayClass` has no namespace because it is cluster-scoped.
- **`spec`:** the desired configuration. This is where the real settings go.

### Step 1: The `GatewayClass`

This object is usually already installed by the networking provider (for example Cilium, Envoy Gateway, or Google Cloud's GKE Gateway Controller). You rarely write it yourself.

```yaml
apiVersion: gateway.networking.k8s.io/v1
kind: GatewayClass
metadata:
  name: eg-gateway-class
spec:
  controllerName: gateway.envoyproxy.io/gatewayclass-controller
```

What the fields mean:
- **`name: eg-gateway-class`:** the name other objects use to refer to this class. A Gateway will say "I use `eg-gateway-class`."
- **`controllerName`:** the unique ID of the controller that handles this class. The controller is installed in the cluster and looks for GatewayClasses with this exact name. This is how Kubernetes knows which software should build the load balancer.

---

### Step 2: The `Gateway` (Operator Defines Listeners)

The DevOps team creates a Gateway that listens on port 80 (HTTP) and port 443 (HTTPS).

```yaml
apiVersion: gateway.networking.k8s.io/v1
kind: Gateway
metadata:
  name: prod-gateway
  namespace: gateway-infra
spec:
  gatewayClassName: eg-gateway-class
  listeners:
    - name: http
      protocol: HTTP
      port: 80
      allowedRoutes:
        namespaces:
          from: All          # Allows developers in ANY namespace to attach routes
    - name: https
      protocol: HTTPS
      port: 443
      tls:
        mode: Terminate
        certificateRefs:
          - name: prod-wildcard-tls
      allowedRoutes:
        namespaces:
          from: Same         # Restricts HTTPS attachment to the same namespace
```

What the fields mean:
- **`namespace: gateway-infra`:** the Gateway lives in the `gateway-infra` namespace, which is owned by the platform team.
- **`gatewayClassName: eg-gateway-class`:** connects this Gateway to the GatewayClass from Step 1. The GatewayClass decides which controller builds it.
- **`listeners`:** a list of "doors" into the gateway. Each listener is one door.
  - **`name`:** a label for the listener. Routes use this name to pick a specific door (you will see `sectionName: http` in Step 3).
  - **`protocol`:** the kind of traffic the door accepts (`HTTP`, `HTTPS`, `TLS`, `TCP`, or `UDP`).
  - **`port`:** the network port the door listens on. Port 80 is the default for HTTP and port 443 for HTTPS.
  - **`tls`:** only needed for encrypted listeners. See the explanation below.
  - **`allowedRoutes`:** decides which routes are allowed to attach to this door. See the note below.

**What `tls.mode: Terminate` means:** The gateway itself decrypts the HTTPS traffic. The traffic inside the cluster then travels as plain HTTP to your Service. `Passthrough` is the opposite: the gateway forwards the encrypted data without opening it.

**What `certificateRefs` means:** This is a reference to a Kubernetes **Secret** (a secure object that stores sensitive data) called `prod-wildcard-tls`. The Secret holds the TLS certificate and private key the gateway uses to encrypt the connection.

> [!IMPORTANT]
> **Cross-Namespace Route Attachment (`allowedRoutes`):**
> Notice `allowedRoutes.namespaces.from`. This gives you strict security boundaries. A cluster admin can set up one central Gateway in `gateway-infra` and let application teams in the `frontend` or `backend` namespaces attach their own routes to it, without giving them admin access to the Gateway itself.
>
> The possible values are:
> - `from: All`: routes from any namespace may attach.
> - `from: Same`: only routes from the Gateway's own namespace may attach.
> - `from: Selector`: only routes from namespaces matching a label selector may attach.

### Step 3: The `HTTPRoute` (Developer Defines Routing)

An application developer deploys an `HTTPRoute` in their own application namespace (`apps`). This object decides which requests go to which Service.

```yaml
apiVersion: gateway.networking.k8s.io/v1
kind: HTTPRoute
metadata:
  name: store-route
  namespace: apps
spec:
  parentRefs:
    - name: prod-gateway
      namespace: gateway-infra
      sectionName: http
  hostnames:
    - store.example.com
  rules:
    - matches:
        - path:
            type: PathPrefix
            value: /products
      backendRefs:
        - name: product-service
          port: 8080
```

What the fields mean, line by line:

* **`parentRefs`:** says which Gateway this route belongs to. It points to `prod-gateway` in the `gateway-infra` namespace, which the developer does not own. The route only works if the Gateway's `allowedRoutes` lets the `apps` namespace attach.
* **`sectionName: http`:** picks one specific listener of the Gateway, the one called `http` (port 80). Without it, the route attaches to every listener that allows it.
* **`hostnames`:** the domain names this route answers for. Only requests for `store.example.com` match. The domain is compared against the HTTP `Host` header, which is the address the client typed in.
* **`rules`:** a list of traffic rules. Each rule has two parts:
  * **`matches`:** the conditions a request must meet. Here, the path must begin with `/products` (`PathPrefix` means "starts with").
  * **`backendRefs`:** where matching requests are sent. Here, the `product-service` Service on port 8080.

Put simply: a request to `store.example.com/products/...` goes through `prod-gateway` and then to `product-service` on port 8080.

### Step 4: Non-HTTP Routes (TCP, UDP, gRPC)

Gateway API is not limited to HTTP. Each protocol needs two things:
1. A **listener** on the Gateway with the matching `protocol`.
2. A **Route** of the matching kind (`TCPRoute`, `UDPRoute`, `GRPCRoute`) that attaches to that listener.

**TCP example (for example, MySQL on port 3306):**

```yaml
apiVersion: gateway.networking.k8s.io/v1
kind: Gateway
metadata:
  name: tcp-gateway
  namespace: gateway-infra
spec:
  gatewayClassName: eg-gateway-class
  listeners:
    - name: mysql
      protocol: TCP
      port: 3306
      allowedRoutes:
        kinds:
          - kind: TCPRoute       # Only TCPRoute objects may attach here
        namespaces:
          from: All
---
apiVersion: gateway.networking.k8s.io/v1alpha2
kind: TCPRoute
metadata:
  name: mysql-route
  namespace: apps
spec:
  parentRefs:
    - name: tcp-gateway
      namespace: gateway-infra
      sectionName: mysql
  rules:
    - backendRefs:
        - name: mysql-service
          port: 3306
```

- **`protocol: TCP`:** the listener accepts raw TCP connections. It does not read the content.
- **`allowedRoutes.kinds`:** limits which route types may attach. Without it, any compatible route could attach.
- **`TCPRoute` has no `matches`:** TCP has no paths or headers to match, so the route only says where to forward the connection.

**UDP example (for example, DNS on port 53):**

```yaml
apiVersion: gateway.networking.k8s.io/v1
kind: Gateway
metadata:
  name: udp-gateway
  namespace: gateway-infra
spec:
  gatewayClassName: eg-gateway-class
  listeners:
    - name: dns
      protocol: UDP
      port: 53
      allowedRoutes:
        kinds:
          - kind: UDPRoute
        namespaces:
          from: All
---
apiVersion: gateway.networking.k8s.io/v1alpha2
kind: UDPRoute
metadata:
  name: dns-route
  namespace: apps
spec:
  parentRefs:
    - name: udp-gateway
      namespace: gateway-infra
      sectionName: dns
  rules:
    - backendRefs:
        - name: dns-service
          port: 53
```

- **`protocol: UDP`:** UDP is connectionless, so there is no handshake. Each packet is forwarded on its own.

**gRPC example:**

gRPC has its own route type. Use `GRPCRoute`, not `HTTPRoute`:

```yaml
apiVersion: gateway.networking.k8s.io/v1
kind: GRPCRoute
metadata:
  name: grpc-route
  namespace: apps
spec:
  parentRefs:
    - name: prod-gateway
      namespace: gateway-infra
      sectionName: https
  hostnames:
    - grpc.example.com
  rules:
    - matches:
        - method:
            service: my.grpc.Service    # gRPC service name
            method: GetData             # RPC method name
      backendRefs:
        - name: grpc-service
          port: 50051
```

- **`method.service` and `method.method`:** match the gRPC service and RPC method. These fields exist only in `GRPCRoute`.

## 5. Built-in Advanced Routing: No More Annotations

Features that used to need messy vendor annotations are now **normal fields** in Gateway API. They are part of the standard, so they look the same on any controller that supports them.

### Feature 1: Native Traffic Splitting (Canary / Blue-Green Deployments)

A **canary release** sends a small share of users to a new version to test it. A **blue-green deployment** runs two full versions side by side and switches traffic between them. Traffic splitting makes both possible without third-party tools like Flagger.

```yaml
apiVersion: gateway.networking.k8s.io/v1
kind: HTTPRoute
metadata:
  name: payment-split
  namespace: apps
spec:
  parentRefs:
    - name: prod-gateway
      namespace: gateway-infra
      sectionName: https
  hostnames:
    - store.example.com
  rules:
    - matches:
        - path:
            type: PathPrefix
            value: /payments
      backendRefs:
        - name: payment-svc-v1
          port: 8080
          weight: 90           # 90% of traffic to stable
        - name: payment-svc-v2
          port: 8080
          weight: 10           # 10% canary traffic
```

- **`backendRefs`:** a list of Services that can receive traffic. When there is more than one, traffic is shared between them.
- **`weight`:** the relative share each backend gets. Here, 90 and 10 add up to 100, so the split is 90% and 10%. The numbers are relative, so `9` and `1` would give the same result.

### Feature 2: HTTP Header & Method Matching

This sends requests to different backends based on HTTP headers (extra data sent with each request) or the HTTP method (`GET`, `POST`, and so on). It is useful for routing internal beta testers to a special version.

```yaml
apiVersion: gateway.networking.k8s.io/v1
kind: HTTPRoute
metadata:
  name: staging-route
  namespace: apps
spec:
  parentRefs:
    - name: prod-gateway
      namespace: gateway-infra
      sectionName: https
  hostnames:
    - store.example.com
  rules:
    - matches:
        - headers:
            - name: X-Environment
              value: staging
        - method: POST
      backendRefs:
        - name: staging-service
          port: 8080
```

How the matching works:
- **`headers`:** matches requests that carry the header `X-Environment: staging`.
- **`method: POST`:** matches requests that use the `POST` method.
- **Two list items mean OR:** a request matches if it meets **either** condition. Each item under `matches` is a separate option.
- **Conditions inside one item mean AND:** if you put `headers` and `method` under the **same** list item, a request must meet **both**. Keep this rule in mind when you write your own matches.

### Feature 3: Native URL Redirects & Rewrites (Filters)

A **rewrite** changes the URL before it reaches the backend. Here, a request to `/old-api/...` is changed to `/api/v2/...` before it is sent. The client does not see the change. This replaces `nginx.ingress.kubernetes.io/rewrite-target`.

```yaml
apiVersion: gateway.networking.k8s.io/v1
kind: HTTPRoute
metadata:
  name: api-rewrite-route
  namespace: apps
spec:
  parentRefs:
    - name: prod-gateway
      namespace: gateway-infra
      sectionName: https
  hostnames:
    - store.example.com
  rules:
    - matches:
        - path:
            type: PathPrefix
            value: /old-api
      filters:
        - type: URLRewrite
          urlRewrite:
            path:
              type: ReplacePrefixMatch
              replacePrefixMatch: /api/v2
      backendRefs:
        - name: modern-api-service
          port: 80
```

- **`filters`:** actions that change the request or the response. Other filter types include `RequestHeaderModifier`, `ResponseHeaderModifier`, and `RequestRedirect`.
- **`type: URLRewrite`:** tells the filter to rewrite the URL.
- **`ReplacePrefixMatch`:** replaces the part of the path that matched (`/old-api`) with the new value (`/api/v2`).

### Feature 4: Request Header Modification

A **filter** can add, change, or remove headers on the request before it reaches the backend. Each entry in `set` and `add` is a `name` and `value` pair. `remove` is a plain list of header names.

```yaml
apiVersion: gateway.networking.k8s.io/v1
kind: HTTPRoute
metadata:
  name: header-mod-route
  namespace: apps
spec:
  parentRefs:
    - name: prod-gateway
      namespace: gateway-infra
      sectionName: https
  hostnames:
    - store.example.com
  rules:
    - filters:
        - type: RequestHeaderModifier
          requestHeaderModifier:
            set:
              - name: x-env          # Replaces the header if it exists, otherwise adds it
                value: staging
            add:
              - name: x-team         # Adds the header, even if one with this name exists
                value: payments
            remove:
              - x-debug              # Removes this header from the request
      backendRefs:
        - name: my-app
          port: 80
```

- **`set`:** sets the value and overwrites any existing header with the same name.
- **`add`:** appends a header. It does not remove existing headers with the same name.
- **`remove`:** deletes the listed headers.

### Feature 5: HTTP to HTTPS Redirect

A redirect sends the client a response that tells them to use a different address. Here, every HTTP request gets a redirect to HTTPS.

```yaml
apiVersion: gateway.networking.k8s.io/v1
kind: HTTPRoute
metadata:
  name: https-redirect
  namespace: apps
spec:
  parentRefs:
    - name: prod-gateway
      namespace: gateway-infra
      sectionName: http        # IMPORTANT: attach only to the HTTP listener
  hostnames:
    - store.example.com
  rules:
    - filters:
        - type: RequestRedirect
          requestRedirect:
            scheme: https
            statusCode: 301    # Permanent redirect. The default is 302 if you leave it out.
```

> [!WARNING]
> **Always set `sectionName`.** Without it, the route attaches to every listener that accepts it, including the HTTPS one. The redirect would then send HTTPS requests to HTTPS again, which creates a redirect loop.

### Feature 6: Request Mirroring

**Mirroring** sends a copy of each request to a second Service. The client only gets the response from the main Service. Mirrored responses are thrown away. This is useful for testing a new version with real traffic.

```yaml
apiVersion: gateway.networking.k8s.io/v1
kind: HTTPRoute
metadata:
  name: mirror-route
  namespace: apps
spec:
  parentRefs:
    - name: prod-gateway
      namespace: gateway-infra
      sectionName: https
  hostnames:
    - store.example.com
  rules:
    - filters:
        - type: RequestMirror
          requestMirror:
            backendRef:
              name: mirror-service   # Receives a copy of every request
              port: 8080
      backendRefs:
        - name: my-app               # Receives the real request and sends the real response
          port: 8080
```

- **`backendRefs`:** the primary Service. Only its response reaches the client.
- **`requestMirror.backendRef`:** the copy destination. Its errors do not affect the client.

## 6. Architectural Comparison: Ingress vs. Gateway API

| Capability | Ingress (`networking.k8s.io/v1`) | Gateway API (`gateway.networking.k8s.io/v1`) |
| :--- | :--- | :--- |
| **API Architecture** | Monolithic (1 single object) | Decoupled & Role-Oriented (GatewayClass, Gateway, Route) |
| **Organizational Personas** | None (Devs and Ops share 1 file) | Distinct personas (Infrastructure Admin, Cluster Operator, App Developer) |
| **Supported Protocols** | HTTP / HTTPS only | HTTP, HTTPS, gRPC, TLS Passthrough, raw TCP, raw UDP |
| **Advanced Features (Weights, Headers)** | Vendor-specific non-portable annotations | First-class, standard YAML fields (`weight`, `filters`, `matches`) |
| **Cross-Namespace Routing** | Awkward / Vendor-specific workarounds | Built in. Access is explicitly allowed with `allowedRoutes` (for routes) and `ReferenceGrant` (for Secrets and Services in other namespaces) |
| **Conformance Validation** | Loose; behavior differs between controllers | Strict test suite that implementations must pass |

**What "conformance" means:** Gateway API comes with a test suite. A controller that claims to support it must pass those tests. So an `HTTPRoute` should behave the same way on Envoy, NGINX, or Cilium. With Ingress, the same YAML could behave differently on each controller.

---

## 7. Summary Reference

* **`GatewayClass`**: "Which controller engine runs the gateway?" (Cluster-wide)
* **`Gateway`**: "Where does external traffic enter? Ports, IPs, TLS certs." (Infra namespace)
* **`HTTPRoute`**: "How do URLs, headers, and paths route to Services?" (App namespace)
* **`ReferenceGrant`**: A permission object. It allows a resource in one namespace to reference a Secret or Service in another namespace. Without it, the cross-namespace reference is refused.

**Quick mental model:** `GatewayClass` picks the engine, `Gateway` opens the doors, and `HTTPRoute` tells the traffic which room to go to.
